    Images, canaries and rolling changes

    This lab models preparing the GPU software stack explicitly in an image. The model guide links the BCM 11 image-management sources. Installed node copies change only when reimaged.

    Promotion workflow

    Prepare gpu-v2 → reimage an idle canary → pass readiness → promote category → roll two idle nodes at a time → check & resume.

    Workload and recovery

    Each job requests whole nodes: eight GPUs per node. Staging, compute, checkpoints and final result publication have separate dependencies. Work units and timing are illustrative.

    State-aware training console

    A finite command subset reads or changes the same virtual model as the controls. It is not an OS shell, a vendor CLI emulator or a way to reach a real host.

    Break one dependency. Follow the consequences.

    Inject or restore a fault

    GPU and mapping faults use the node selected in Nodes. The number applies to rails (1–8), bond members (1–2) or storage services (1–4).

    Suggested experiments

    1. Run a job, interrupt rail3 and inspect the failed collective. Repair it and explicitly requeue from the last committed checkpoint.
    2. Lose one NS member. Compare LACP capacity and active–backup behavior. Lose both; observe where application I/O waits.
    3. In Lustre, interrupt the active metadata service and follow modeled HA recovery. Then interrupt an OSS.
    4. In GPFS, lose one quorum voter, then two. Quorum and data-copy availability are separate gates.
    5. Try the unprepared gpu-v2 canary. Preparing the image does not modify its installed copy; reimage before promotion.
    6. Drain a busy node. Existing work may finish, but a new job must wait for suitable ready resources.

    “Repair all” restores modeled faults but preserves images, drains and checkpoints. Failed jobs never become completed merely because a fault was cleared.
